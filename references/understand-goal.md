# 需求澄清

## 何时进入

表面请求与真实结果间仍需推断，或目标、事实、取舍、验收、范围、授权、项目入口有方向性缺口时进入；不等用户点名，原始需求也只是输入。轻任务结果明确时快速通过。

## 已知输入

- 用户原始请求、已表达偏好与业务背景；
- 项目规则、README、配置、入口代码、测试、历史计划和可用工具；
- 已证实事实、带来源的推断、约束、现有真源与能力边界；
- 谁为结果负责、什么外部动作需要授权；
- 已回答问题、仍开放的决策分支、用户明确延期项与当前理解快照。

## 深度判断

先判断结论是否依赖可变项目现状。**新需求**若依赖，必须在**调研前**使用项目定义的 freshness 机制刷新目标真源并**固定 source fingerprint**；调研、方案和后续实施沿用同一现场，交付前再按项目契约同步一次。纯概念问答不触发刷新，恢复同一需求继续已绑定现场并记录目标漂移，**不按落后提交数设置阈值**，也不在每个动作重复刷新。代码型调查的最小 fingerprint 是 `HEAD SHA + git status --short + git diff --name-only`；未提交变更属于当前事实，不能只读 HEAD。

调查按最小定位推进：先读项目入口和 Active 索引的命中章节，再以 Markdown 标题、代码符号或字段名定位并读取相邻上下文；不全文读取计划、规范或巨型源文件。只有命中不足以判断时才扩大范围。

先建立最小**目标链**：**表面请求 → 当前痛点 → 本质目标 → 成功信号**；四节点分别回答用户要什么、为何现在、拿掉预设方案后真正改变什么、什么证据算成。每一跳标明事实、推断或未知。

先做**价值门 A**：这件事解决谁的什么问题，结果为何值得投入 AI、什么信号说明值得继续。再问一句：如果现在进入下一动作，是否必须猜关键事实，或无法验证结果？

把未知只分为四路：

- **事实可查**：可从项目、数据、工具、配置或可信来源获得；AI 自己查。
- **取舍待定**：价值、优先级、风险接受度或主观方向需要决策 owner 选择。
- **假设待验**：继续讨论不会变成事实，应以实验、原型、小样或可失败验收验证。
- **外部待解**：依赖权限、凭据、外部 owner、生产事实或明确授权。

再过**调研充分性硬门**。事实调查固定按最短证据梯推进：**项目真源 → 已连接工具与数据 → 官方一手来源 → 最小实验**；前一层足够就停止，不为显得充分而继续扩张。每轮只问“新增证据是否仍可能改变目标、范围、方案或风险”；答案为否时记录停止依据，答案为是却没有继续调查、实验或转成 blocker 时不得进入需求成熟度判断。二手总结只能帮助定位一手来源，不能在有一手来源时替代它。

再过**需求成熟度硬门**，逐项检查五个承重分支：

1. **用户 / 场景 / 现状痛点**：谁在什么情况下遇到什么问题，当前如何替代，为什么现在值得改变；
2. **目标结果与可观察成功标准**：做成后谁能完成什么，什么证据说明有效；
3. **范围与非范围**：本次必须覆盖、明确不做和可以延期什么；
4. **关键约束、优先级与取舍**：时间、质量、成本、体验、风险冲突时先保什么；
5. **授权边界与责任人**：谁能决定，哪些外部动作、数据或风险需要授权。

每个分支必须有可追溯处置：事实有来源，承重决策有用户回答或明确委托，真假未知有可验证假设，范围外依赖有明确 blocker。**两个合理答案会形成不同的需求契约或重大风险承诺**——改变目标或用户结果、可观察验收、范围或优先级、关键取舍、授权边界或难逆风险——就是承重决策，由**用户选择或填写**，也可由用户明确委托 AI 在给定边界内决定。AI 给出完整推荐，**沉默不等于确认**。

后续输入可高置信判为用户的**最新目标或要求**时，直接**覆盖旧结论**并只重算受影响分支；覆盖意图不清或误判有实质风险时才**先向用户确认**。新旧决定不并列。

调查后直接展示**推荐需求契约（待确认）**：目标、结果、验收、范围/非范围、取舍、授权、证据、AI 建议和 **AI 代选细节（可调整）**。它是**默认需求发现界面**，让用户整体确认并按需调整；三道门和明确确认前不能登记成果，**沉默不等于确认**。

局部、可逆且所有合理选择仍落在同一需求契约内的细节，由 **AI 代选**。选择依据按**项目约定、当前背景和稳定历史偏好**收敛，并在契约中按主题合并展示，用户有异议时直接调整。事实可查项继续由 AI 调查；承重决策进入用户注意力路径。

存在承重决策时，在当前 owner 内进入 **Grill 深度**并建立**有界承重决策树**。**每条分支当前最上游**的未决承重节点组成当前 `frontier`，其中**相互独立的承重问题一次集中展示**；每题提供稳定树形编号、当前理解或推荐、**选项或填空**，以及**答案会改变什么**。回答或委托关闭当前节点并展开相关子节点，**每轮回答后重算** frontier；含糊或冲突沿用原编号继续收敛。

每轮经过**契约稳定门**：事实已有来源，所有可达承重分支归入**用户已决定**、**明确委托 AI**、**可验证假设**、**明确延期**或有 owner 与解锁条件的 **blocker**，且**剩余项均可由 AI 代选**。达到稳定门后展示完整需求契约并请求整体确认；用户修正契约时只重算受影响分支。**题数和轮数由实际决策树自然收敛**。

## 核心动作

1. 刷新需要 fresh 的目标真源并固定现场；代码型结论先记录最小 Git fingerprint，再按标题/符号读取最小上下文。沿证据梯区分事实、推断和未知。事实可查不问用户，只问不能自行发现的关键问题。
2. 建目标链，区分承重决策与 AI 代选细节，形成带推荐、理由和代价的完整契约。
3. 建必要决策树；同批展示当前 frontier 的独立问题，回答含糊或冲突时沿用同一编号。
4. 用短反馈回路重算 frontier 并检查契约稳定门；代选细节按主题写入契约。
5. 三道门通过后请求确认完整契约；用户修正只重走受影响门。
6. 确认后才登记成果；优先补现有真源，无 owner 时最多一份短入口文档。

## 写入真源

复杂项目把目标链、四路未知、三道门、决策树、关键例外、契约、确认及来源写入 `findings.md`，确认后同步 `task_plan.md`。标准任务留在对话，仅恢复需要时写最小计划；轻任务不写。

## 停止 / 通过

三道门通过；fresh 需求已固定 source fingerprint；五个承重分支有来源、回答、明确委托、假设或 blocker；AI 代选细节已随契约展示。契约稳定门通过且标准/项目任务已明确确认完整契约后进入下一动作。无价值或现状已满足可 no-op。

## 失败回路 / 能力缺口

事实不可得时转为假设或外部待解。承重决策可以由用户回答、明确委托、延期、缩围或转为 blocker；AI 代选承载契约内的安全可逆细节。缺权限或授权时写清 owner 和解锁条件；能力缺失时标明未覆盖范围。
