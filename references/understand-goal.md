# 需求澄清

## 何时进入

表面请求与真实结果间仍需推断，或目标、事实、取舍、验收、范围、授权、项目入口有方向性缺口时进入；不等用户点名，原始需求也只是输入。轻任务结果明确时快速通过。

## 已知输入

- 用户原始请求、已表达偏好与业务背景；
- 项目规则、README、配置、入口代码、测试、历史计划和可用工具；
- 已证实事实、带来源的推断、约束、现有真源与能力边界；
- 谁为结果负责、什么外部动作需要授权；
- 已回答问题、仍开放的决策分支、用户明确延期项与当前理解快照。

## 深度判断

先判断结论是否依赖可变项目现状。**新需求**若依赖，必须在**调研前**使用项目定义的 freshness 机制刷新目标真源并**固定 source fingerprint**；调研、方案和后续实施沿用同一现场，交付前再按项目契约同步一次。纯概念问答不触发刷新，恢复同一需求继续已绑定现场并记录目标漂移，**不按落后提交数设置阈值**，也不在每个动作重复刷新。

先建立最小**目标链**：**表面请求 → 当前痛点 → 本质目标 → 成功信号**；四节点分别回答用户要什么、为何现在、拿掉预设方案后真正改变什么、什么证据算成。每一跳标明事实、推断或未知。

先做**价值门 A**：这件事解决谁的什么问题，结果为何值得投入 AI、什么信号说明值得继续。再问一句：如果现在进入下一动作，是否必须猜关键事实，或无法验证结果？

把未知只分为四路：

- **事实可查**：可从项目、数据、工具、配置或可信来源获得；AI 自己查。
- **取舍待定**：价值、优先级、风险接受度或主观方向需要决策 owner 选择。
- **假设待验**：继续讨论不会变成事实，应以实验、原型、小样或可失败验收验证。
- **外部待解**：依赖权限、凭据、外部 owner、生产事实或明确授权。

再过**调研充分性硬门**。事实调查固定按最短证据梯推进：**项目真源 → 已连接工具与数据 → 官方一手来源 → 最小实验**；前一层足够就停止，不为显得充分而继续扩张。每轮只问“新增证据是否仍可能改变目标、范围、方案或风险”；答案为否时记录停止依据，答案为是却没有继续调查、实验或转成 blocker 时不得进入需求成熟度判断。二手总结只能帮助定位一手来源，不能在有一手来源时替代它。

再过**需求成熟度硬门**，逐项检查五个承重分支：

1. **用户 / 场景 / 现状痛点**：谁在什么情况下遇到什么问题，当前如何替代，为什么现在值得改变；
2. **目标结果与可观察成功标准**：做成后谁能完成什么，什么证据说明有效；
3. **范围与非范围**：本次必须覆盖、明确不做和可以延期什么；
4. **关键约束、优先级与取舍**：时间、质量、成本、体验、风险冲突时先保什么；
5. **授权边界与责任人**：谁能决定，哪些外部动作、数据或风险需要授权。

每个分支必须有可追溯处置：事实有来源，主观取舍有用户回答，真假未知有可验证假设，范围外依赖有明确 blocker。会改变目标、范围、验收、优先级或授权的判断必须由用户作答或明确延期；AI 可以给完整推荐，不能把推荐伪装成用户决定，**沉默不等于确认**。只有局部、可逆且不改变结果的实现细节才可采用已声明默认。

后续输入可高置信判为用户的**最新目标或要求**时，直接**覆盖旧结论**并只重算受影响分支；覆盖意图不清或误判有实质风险时才**先向用户确认**。新旧决定不并列。

完成最短必要调查后，直接展示一份完整的**推荐需求契约（待确认）**，把目标、用户结果、验收、范围/非范围、关键取舍、授权边界、证据和 AI 默认建议放在同一处。契约是**默认需求发现界面**：用户纠正关键例外，而不是先回答长问卷；它在三道门通过并获明确确认前仍是待确认提案，不能登记为完成成果或进入下一动作。

默认最多一批高价值问题，每批 **1–3 个最高杠杆问题**。**问题杠杆** = 决策变化 × 不确定性 × 错判代价 − 用户成本；只问无法自行发现且会改变目标、范围、优先级、验收或授权的**关键例外**，优先抓住**为什么做、真正要改变什么、什么结果最重要**，不做固定问卷。每题先给 AI 的**当前理解或推荐**，再说明答案会改变什么。只有仍存在会改变目标、范围、验收或授权的未知，且第一批暴露新上游依赖或冲突，才允许**第二批**并指出**实质缺口**；不得为再确认而追问。轻任务可信、可逆且结果明确时零追问。

## 核心动作

1. 结论依赖可变项目现状的新需求先刷新目标真源、固定 source fingerprint 和任务现场，再按证据梯检查项目真源、已连接工具与数据、官方一手来源和必要的最小实验；把事实、推断和未知分开并标来源，不做全仓资料考古，事实可查就不问用户，只询问不能自行发现的关键问题。
2. 建立目标链；相互依赖的未知才建最小**决策树**，不转成问题清单。
3. 直接形成一份**完整推荐**契约；事实与推断分开，关键取舍给推荐、理由、代价和默认假设，显式标记待确认。
4. 按问题杠杆排序并稳定编号；**回答含糊**、回避或冲突时沿用**同一编号**指出缺口，仅在会改变目标、范围、验收或授权时继续。
5. 收到回答后更新契约和必要的决策树；第一批暴露新的实质缺口时才生成第二批，否则停止追问。
6. 使用**短反馈回路**：让用户一次纠正会改变目标、范围、验收或方向的关键理解，不把方向决策积压到长问卷末尾；用户原请求和可信真源已覆盖全部承重分支时可零追问。
7. 三道门通过后请求用户明确确认当前完整契约；用户修正承重项时只重走受影响门，不沿用旧确认。
8. 需求契约确认后才登记成果；信息存在但分散或过期时优先补现有 README、规则或真源。没有 owner 且缺口确实阻断时，最多一份短入口文档；只做导航，不复制部署、安全、设计或运行细节。

## 写入真源

复杂项目把目标链、四路未知、三道门、决策树、关键例外、推荐契约、确认及其事实/来源/推断写入 `findings.md`，确认后同步 `task_plan.md`。标准任务留在对话，仅持久恢复时写最小 `task_plan.md`；轻任务不写。已有 owner 原位补齐。

## 停止 / 通过

价值门 A、调研充分性硬门和需求成熟度硬门均已通过；依赖可变项目现状的新需求已有 fresh source fingerprint，五个承重分支都有来源明确的事实、用户回答、可验证假设或 blocker，不再存在被 AI 默认替代的关键用户判断。轻任务符合快速通道，或标准任务/项目任务的需求契约已获明确确认；下一动作无需猜关键事实，继续调查或追问已不再改变目标、范围、方案或风险时停止。无业务价值、证据证明无需做或已有结果满足时，允许以 no-op 结束。

## 失败回路 / 能力缺口

事实不可得时转为假设待验或外部待解，不编造。存在关键取舍、含糊回答、覆盖意图不清的矛盾或用户要求压力测试时必须加载决策挑战 harness；明确修正直接覆盖。用户暂不回答时，只能对安全可逆的局部项采用已声明默认，关键判断则缩小范围、明确延期或保持 blocker。缺凭据、权限或高风险授权时写清 blocker、外部 owner 和解锁条件。无网络、浏览器或 memory 时改用仓库与当前对话证据并标未覆盖项，不把能力缺口伪装成事实。
