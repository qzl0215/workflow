# 结果规划

## 最小动作

从已接受的结果契约反向规划：先确定证明整体结果需要哪些责任，再把责任拆成可独立执行和验收的任务。最小计划应能回答：

- 哪项用户结果由谁负责闭环；
- 每项验收由什么产物和什么证据覆盖；
- 哪些依赖决定串行，哪些责任可以并行；
- 哪些高风险未知应先用最小验证消除；
- 集成后如何证明整体结果，而不只是各任务完成。

简单任务可以只有一个任务，不为使用编排或子智能体而强行拆分。

## 最小停止条件

进入任务执行前，计划至少满足：

- 结果契约中的每项验收都有明确实现责任和验真路径。
- 当前可执行任务的输入、边界、授权和完成证据足够清楚。
- 依赖来自真实信息或产物关系，不是习惯性的阶段顺序。
- 写冲突、集成责任和失败回流点可控。
- 删除或合并任一任务都会损失独立结果、风险隔离或证据价值。

不要求所有远期细节提前写死。只要整体覆盖成立，后续任务可在上游证据产生后渐进细化。

## 触发与按需展开

| 信号 | 扩展动作 |
|---|---|
| 单一局部结果、责任不可再独立 | 保持单任务，由同一责任者执行和验真 |
| 多个责任共享同一输入但互不依赖 | 读取 [任务编排](orchestrate.md) 判断并行收益 |
| 下游必须消费上游决定、接口或证据 | 建立显式依赖，按证据串行 |
| 高风险未知会使大部分实施失效 | 先规划最小实验、探针或薄切片 |
| 一个任务跨越过多上下文或无法独立验收 | 沿结果边界继续拆分，而不是按文件数量拆分 |
| 拆分后协调、写冲突或集成成本高于收益 | 合并责任或改为同一责任者串行完成 |
| 计划过程中发现目标或验收不成立 | 返回 [目标框定](frame.md)，不在计划里偷偷改契约 |

每次只展开当前需要的深度。计划不是一次性预测全部过程，而是保持结果覆盖不变的可更新责任图。

## 结果优先拆分

优先按“可独立证明的结果”拆分，而不是按目录、技术层、角色名称或预计工时拆分。一个好任务应当产生可被下游消费或可独立验真的状态变化。

适合独立任务的边界通常包括：

- 独立的用户能力或兼容承诺；
- 风险较高、可先证伪的技术假设；
- 有清晰输入输出契约的组件或迁移；
- 可以独立取得的新鲜证据；
- 需要隔离文件域或授权的工作。

如果两个任务只有一起完成才有意义、共享大部分上下文且无法分别验真，把它们交给同一责任者通常更稳。

## 覆盖证明

计划责任者必须能从结果契约双向走通：

- 从每项验收找到负责的计划、任务、集成点和验真证据；
- 从每个任务找到它服务的结果、风险或证据缺口。

前者防止漏项，后者发现冗余。没有下游消费者、没有独立风险、也不增加证据强度的任务应删除。

任务全绿只说明局部契约成立。整体结果仍由计划责任者在集成后负责，不得把它分摊到无人承担。

## 串并联原则

只让真实依赖决定串行：上游决定、接口、数据、授权或证据尚未产生时，下游等待。仅仅属于传统流程的先后关系，不构成依赖。`Plan` 与 `Task` 的串并联由依赖决定，不是为了凑并行。

并行需要同时具备：

- 责任边界可以独立描述；
- 输入和验收在开始前足够稳定；
- 文件域或写入权不冲突，或已有明确集成责任；
- 并行节省的关键路径时间大于合成和沟通成本；
- 失败能局部回流，不会让其他分支大面积作废。

不要预设智能体数量。并行度由就绪责任、风险、工具能力和集成成本动态决定；缺少子智能体时，同一计划仍可顺序执行。

## 任务胶囊

每个委派任务使用最短但充分的胶囊。形式可以自由，责任者必须能看出：

- `P/T` 标识和它服务的结果；
- 要产生的状态变化，而非只列操作；
- 已接受输入、授权，以及确实会改变执行的按需边界；
- 可写范围与共享资源边界；
- 完成条件、验证方式和需返回的候选证据；
- 真实依赖、可消费的上游产物和失败时回流对象。

胶囊同时携带目标契约、父计划结果和当前任务的身份摘要，例如 `contract_hash`、`plan_contract_hash` 与 `task_contract_hash`。摘要用于发现开始后的契约漂移，不代替契约内容；协调者只重新判断受变化影响的范围。

已在共享真源中的稳定上下文只给入口，不复制长篇背景。一次性关键约束直接写进胶囊，避免责任者猜测。

胶囊默认内联发送；跨会话、昂贵上下文或需要恢复时才物化。子任务责任者不得把自己的完成判断直接写成 `work.md` 的已接受事实。

## 思考深度与子计划

思考深度由风险和不确定性决定，不由任务大小标签决定。难逆、高影响、跨边界或证据薄弱的任务，应在执行前补强失败模型、验证路径和恢复边界；局部可逆任务保持轻量。

只有当一个任务内部存在多个可独立验收、可独立调度的结果责任时，才建立子计划。子计划继承上级结果和授权，不重新发明目标。继续拆分到责任者能够独立行动且协调成本合理即可，不追求最细粒度。

## 方案就绪

首次状态变更前，把内部计划翻译成用户真正能判断的方案：目标、推荐方案、验收和交付路径。改动范围、替代方向、风险与其他边界只在它们会改变用户决定时展开。

方案涉及浏览器中的视觉或交互调整时，先读取 [体验探索](experience.md)，在确认前展示基于真实源码的局部视觉演示。目标区域承载候选变化，原页面其他元素作为保护面继续复用；用户看过截图或可访问预览并理解实际影响后，再确认是否开动。

用户确认或明确委托后，方案就绪。用户说“开动”“开始执行”或同等明确的话时，它既确认当前方案，也启动连续兑现；已经在同一请求中给出精确方案和执行信号时直接通过。用户确认的是目标、推荐方向、验收和交付路径，不需要审核内部每个微任务。

方案就绪后，安全可逆的拆分、调度与实现细节由模型连续推进。后续只有计划实质改变结果、风险、代价或授权时才重新确认。

## `work.md` 中的计划投影

需要持久控制面时，只记录当前有效的结果责任、父计划整体验真、依赖、状态、下一就绪项和已接受证据定位。只有当前就绪责任展开任务所需输入/真源、授权/按需边界、验证/返回条件；等待任务仅保留结果、依赖、状态与细化触发，成为就绪责任后再展开。任务字段只写相对目标契约的增量，继承内容不重复。物化的上下文包、候选回执或昂贵证据只登记恢复入口，不复制正文。删除被新决定取代的当前投影，不保存状态翻转流水。

协调者是唯一写入者。任务责任者返回候选回执，协调者检查契约和证据后再接受。简单任务留在上下文，不为使用模板而创建 `work.md`。

## 结果承载检查

每个任务、依赖、文档和验证都标明它独立保护的结果、风险或证据缺口；价值与其他项完全相同且合并后质量不变时，自然合并。

文件数量、模型能力、可用并行度、旧流程习惯或形式完整感都不构成独立价值。简单是质量成立后的自然结果，不是预先削弱质量。

## 输出与回流

输出当前结果计划、就绪责任、必要依赖、整体集成与验真路径。后续执行暴露新事实时，只重算受影响的依赖和任务；结果契约未变就不全量重写计划。

若计划无法为某项验收找到责任，返回目标框定澄清结果；若只是执行路径失败，转入恢复处理，不用重新讨论已经稳定的目标。
