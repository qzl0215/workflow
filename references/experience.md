# 体验探索

体验方向不确定、呈现差异会影响选择，或需要验证真实交互时使用。明确用户要完成的任务、关键路径和可能失败的位置；局部呈现已明确时直接实施。

文字不足以支持决定时，选择最小样例、草图、截图或可访问预览。只有真实互斥方向需要比较时才增加方案。用户要求先预览后修改时遵守该顺序；否则不把演示设为所有状态变更的前置批准门。

演示开始前明确它要支持的决定和用户应观察的关键差异；演示完成不是默认终点。若方向仍待用户选择，交付时说明当前是方向确认还是成品验收、推荐及理由、备选的关键代价、已经证明与尚未证明的边界、可直接回复的选择，以及确认后继续的实现和验真；不能只发链接或泛问反馈。方向已确认且实施已有授权时，演示只作为执行证据继续推进，不重新制造确认门。

## 方案 demo 页

大事的方案选项做成一个可视化页面让用户选；宿主不能渲染页面时退回短表。页面只服务“选哪个”这一个决定。

内容按用户的阅读习惯排：

- 第一屏是结论：推荐哪个、为什么。往下每个方案一块，能并排就并排。
- 每个方案用图或可操作的小样例展示做完的样子，再写和现在比变了什么、收益、要背的代价。高管评估留下的分歧写在对应方案下。
- 简单短句、业务语言、图先于字；一个东西只有一个名字；不写制作过程。
- 结尾给可直接回复的选择，如“选 A”。

做页面的方法取自 page-craft，本机装有时调用它；没装就按这个顺序：定读者 → 按读者思路排顺序 → 定用语 → 做呈现 → 对整页做减法（拿掉它用户不会看错就删）→ 电脑和手机宽度各截一张图自己看过再交。

写 HTML 和 CSS 的底线取自 Google 的 modern-web-guidance。有网络时先查再写，每个界面能力查一次：

```bash
npx -y modern-web-guidance@latest search "<2–5 个英文词，如 responsive data table>"
npx -y modern-web-guidance@latest retrieve "<id>"
```

查不了时守住这几条：

- 优先用浏览器原生能力，不手写替代品也不为它加依赖：弹层用 `<dialog>` 和 popover，折叠用 `<details>`，动作用 `<button>`，跳转用 `<a>`。
- 语义结构：一个 `<h1>`，标题不跳级，内容放进 `<main>`、`<nav>` 等区域，设置 `lang` 和 viewport。
- 只用主流浏览器都已普遍支持的特性（Baseline Widely available）；更新的特性要带降级。
- 颜色、字号、间距定成一小套 CSS 变量；跟随系统深浅色；手机宽度不横向滚动；尊重系统的减少动效设置。
- 键盘能操作、焦点看得见，文字对比度够，图有文字替代。

demo 只证明方向可供判断，不是成品验收。

## 真实页面

现有页面优先复用真实源码、组件、数据与权限逻辑，只改目标区域。不要为局部修改模拟整页或建立第二套实现。项目已有预览、隔离环境和测试数据时优先复用；新增独立验收路由只是有明确收益时的可选方案。

验证关键交互、受影响布局和相关权限链路。源码未改不等于行为完全不受共享样式、配置或依赖影响，应检查实际连接点；边界可证明独立时不要求全页人工对比。

真实登录态或数据不可用时，用真实实现与脱敏样例证明当前覆盖部分，并说明边界。方向演示不能替代成品验收，本地呈现不能证明生产权限和数据链路；真实入口可用后补充对应证据。任何测试写入仍受现有授权与数据隔离约束。
