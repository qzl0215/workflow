# 诊断

用户说“诊断”时使用，技术问题和业务问题都适用。目标按顺序是：用户先恢复好的体验，问题不再发生，造成问题的工作方法或规范被补上。

## 分诊

先查清这三件事，查得到的不问：

| 查什么 | 用来 |
|---|---|
| 好是什么样：用户原话里期望看到什么 | 后面每一步都对照它验收 |
| 影响谁、多大、持续多久 | 决定要不要先止血 |
| 最近变了什么，上一个正常的状态 | 最快的止血和最可能的根因常在这里 |

## 先拿复现信号

推根因之前，先拿到一个对这个问题会变红、修好会变绿的信号，并且已经跑过一次：

| 问题 | 信号 |
|---|---|
| 代码、接口、构建 | 失败的测试、curl、固定输入的命令 |
| 页面 | 真实交互脚本，或带时间的截图 |
| 数据、指标 | 一条查询，结果和用户说的不对对得上 |
| 内容、知识库、模型回答 | 一个真实样例的输入和输出 |
| 流程、协作、AI 会话 | 真实记录里出错那一步的原文 |

- 信号要复现用户说的那个症状，不是旁边的另一个问题；尽量快、稳定、自己能跑。
- 拿不到就停下，说试过什么，向用户要环境、日志、录屏或加临时观测的许可，不靠读代码猜。
- 本机装有 `diagnosing-bugs` 时，代码问题按它构建和缩小复现。

## 推根因

- 先列 3–5 个能证伪的假设并排序，每个写出预测：“如果是 X，改 Y 问题就消失”。说不出预测的不算假设。把排序给用户看，他常能一眼排除几个；不等回复也继续。
- 一次只改一个变量。调试日志加统一前缀，收尾时一次清掉。
- 同一假设重复且没有新观察，换本质不同的实验：往上看调用方，往下看底层，换工具，或和上一个正常状态对比。再次失败按[验真](prove.md)处理。
- 根因成立的标准：能解释全部症状，按它改了信号就变绿。

## 止血和修源头

用户体验优先。源头修复在用户等得起的时间内做不完，就先止血。

| | 止血 | 修源头 |
|---|---|---|
| 目的 | 用户先恢复 | 问题不再发生 |
| 常见做法 | 回滚、关开关、切备用、给用户绕行办法 | 改根因，加回归测试 |
| 授权 | 用户说诊断，就授权了能回退的止血，线上也一样；记下怎么回退。回退不了、会删数据或扩大外部影响的先问 | 按正常授权 |
| 验证 | 在用户入口看体验恢复 | 复现信号变绿，原始场景再跑一次 |

- 止血标明是临时的，写清什么时候撤；源头修好后撤掉，或说明为什么留着。
- 回归测试只写在能复现真实调用链的位置；找不到这样的位置本身是一条发现，放进复盘。
- 修完查一遍同类问题，列出来给建议，不顺手改。

## 复盘：根因的根因

每次诊断收尾都给。问“为什么这道防线没拦住”，问到能落成一个具体改动为止：

| 缺的防线 | 例子 | 建议改哪 |
|---|---|---|
| 规则没有或写错 | 项目没约定接口超时 | 项目规则或决策资料 |
| 规则有但没生效 | 全局文件还用旧名“开干流程”，模型照旧名走 | 改入口、删冗余或旧叫法 |
| 缺自动检查 | 发布检查不扫已退役的叫法 | 测试、lint、hook、CI、发布检查 |
| 找不到或拿不到信息 | 日志没接，文档没入口 | 补入口或只读访问 |
| 结构锁不住问题 | 没有能写回归测试的位置 | 结构改进建议 |
| 工作方法 | 没复现就改，没验证就说修好 | 技能改进提案 |

- 工具能稳定判断的做成检查，不写成提醒；要靠判断的才写规则。
- 找机制，不找人。
- 只提案，用户批准才改。改技能的按[复盘](learn.md)的技能改进提案写。

## 收尾

先给结论，按这个顺序：症状（用户原话）→ 根因和证据 → 止血（做了什么、怎么回退、什么时候撤）→ 源头修复 → 同类问题 → 防线建议。没证明的直说。

查不出时也要交代：已证实什么、已排除什么、缩小到了哪里、下一步需要什么。
