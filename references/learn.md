# 复盘

用户确认或纠正了自己、团队或项目的背景和偏好，要求复盘或记住，同一类失误第二次出现，或用户指出做法本身不对时使用。没有新内容就结束，不做空复盘。

## 存什么

只存会改变以后行动的稳定事实、决定，或难以便宜重查的证据。本技能不存具体项目的知识。

| 内容 | 写到哪 |
|---|---|
| 业务规则和决定 | 项目的产品或决策资料 |
| 实际行为和发布入口 | 代码、配置和操作说明 |
| 进度 | 当前任务 |
| 内容有但难找 | 补入口，不复制正文 |

## 用户和项目背景

目标是越用越懂用户：常用的背景和偏好记一次，以后开工先读，不再问。用宿主已有的记忆，本技能不另建存储。

| 内容 | 记到 |
|---|---|
| 跟人走的：用户是谁、团队是谁、长期偏好 | 用户级记忆 |
| 跟项目走的：项目服务谁、业务背景、项目约定 | 项目级记忆或项目已有的说明文件 |

- 用户确认或纠正过的才记成事实；自己推测的标成推测，或等确认后再记。
- 记下后用一句话告诉用户记了什么，用户可以当场否掉。
- 已有同一条就更新，不新增；过时的删掉。
- 宿主没有记忆功能时只在本次会话里用，不另建文件。

## 怎么写

- 已确认的决定、实际观察、未验证的假设分开写；不把模型的建议写成用户的政策，不把计划写成已上线。
- 旧决定被替代时，注明被什么替代和原因。
- 改业务政策或改本技能要有对应授权。

## 同一问题再次出现

1. 先查是不是目标、规则或共享实现错了。
2. 工具能稳定判断的，修自动检查，不只加提醒。
3. 是本技能的规则没管住，写一条技能改进提案。

## 技能改进提案

技能靠它进化：真实工作里暴露的失效变成提案，用户批准才改。同一类失误第二次出现，或用户指出做法本身不对，而原因在本技能的规则（没写、写了没触发、写错了）时，写一条。

| 栏目 | 写什么 |
|---|---|
| 现象 | 发生了什么，用户的原话，在哪个环节；两次都写 |
| 原因 | 哪条规则没管住：没有这条，有但没读到，还是规则本身不对 |
| 改哪段 | 文件和位置，改前和改后的原文 |
| 不改的代价 | 下次还会多出什么返工 |

- 每个会话最多一条，挑返工最多的那类。只发生过一次的不提。
- 在本轮汇报的末尾提给用户；本机有技能维护者的提案台账时同时记进去。
- 只提案，不改技能，不改常驻习惯文件；用户批准后按技能项目的贡献流程改。
- 原因在目标、项目规则或工具上的，按上面第 1、2 步处理，不写提案。
