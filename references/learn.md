# 经验复盘

## 负责什么

在没有交付目标时，于结果已经验真后；在有交付目标时，于交付状态已经确定后，判断这次有什么值得改变未来决策。每个面向用户的目标完成并陈述结果后都会先做一次最小优化识别；复盘只展开有事实依据的候选，不把内部测试、提交等微步骤逐个变成新复盘。没有稳定复用价值时，最优结果就是 `no-op`。

最小优化识别本身不是新增核心阶段：无可行动发现时简洁说明 `no-op`；出现可行动候选时进入 `learn`。有真实交付目标时遵循 `prove → deliver → 完成陈述 → learn`，没有交付目标时在 `prove` 与完成陈述后进入。任何线程发生上下文压缩，都成为稳定治理信号，本次复盘自然包含下述检查；压缩事件不直接证明治理存在缺陷，检查后仍可得到 `no-op`。`learn` 不负责发布，也不能修改交付事实。

## 最小入口与最小动作

先确认原目标的完成事实已经向用户陈述，再用一次最小偏差检查回答：原本预计什么、实际发生什么、差异有什么证据、哪个早期信号下次会改变行动。没有明显偏差、风险、返工或可复用收益时，以 `no-op` 结束，默认不持久化这个空结果。发生过上下文压缩时，复盘增加下面的上下文治理与结果承载检查。

只基于实际证据提候选，不把模型感想、成功叙事或偶然噪音直接升级为长期规则。最小识别分别检查项目级更新与 workflow 级更新；同一发现指定一个主要责任层级，避免两边重复回灌。有可行动候选时，面向用户给出问题诊断、事实证据、实际影响、推荐方案与验收方式，并等待用户确认是否把它启动为新的目标。多个相关候选合并到一次决策边界，补充备选取舍、不处理的影响和最短回复；用户可以直接接受推荐、分别选择，或明确委托模型决定是否建立新目标。

## 默认快路

1. 原目标完成陈述后，发生过上下文压缩时先吸收本文件的压缩治理检查；否则找出造成最多返工、等待、`token`/交互浪费或风险暴露的事实。分别判断项目级更新和 workflow 级更新；价值相同的发现合并，两类都没有可行动发现就展示双 `no-op`，直接结束且无需用户回复。
2. 把每项写成经验候选：触发证据、影响范围、建议的最小改动、唯一责任者、验收方式、不处理的代价，以及未来什么场景会改变哪个决定或动作。项目级只承接当前项目成立的问题；workflow 级只承接跨项目稳定成立的协议问题。
3. 检查现有代码、测试、配置、`README`、项目规则或技能是否已经表达；找到唯一责任者和入口，不为经验另建竞争真源。
4. 等交付事实确定后再接受涉及交付的经验。协调者确认消费价值、证据和责任者后，才将候选变为已接受经验。接受候选不等于完成回灌，也不能直接修改长期真源。
5. 把已接受候选翻译成用户可判断的问题诊断与推荐方案；浏览器视觉调整先按 [体验探索](experience.md) 展示局部保真的视觉演示，再交给用户确认。
6. 对每个项目级或 workflow 级候选，用户分别选择“回灌 / 延后 / 放弃 / 委托 AI 决定”。选择记录为 `writeback_receipt`；“回灌”只授权建立新需求，不授权实施。
7. 选中回灌的项目级更新与 workflow 级更新分别成为独立新目标，各自重新经过需求澄清、需求确认、适配型演示、方案确认和用户说“开动”，再走 `execute → prove`；需要外部写入时再走 `deliver`。它们不共享原任务或彼此的执行授权，也不改变原任务已经成立的完成事实。
8. 清理只用于本次判断的临时材料；需要审计、回滚或恢复的证据进入已有证据系统，不另建档案流程。

## 上下文压缩带来的治理检查

上下文压缩是治理信号，不是缺陷结论。基于压缩前后可见事实、恢复时重新查找或重建的内容、重复加载与交接痕迹进行判断；平台没有可靠遥测时，将 `token` 数、压缩损失或成本保留为未知。

1. **找到唯一责任者**：只在当前项目成立的问题回到项目规则、文档、脚本或代码入口；跨项目反复成立的问题回到 workflow 现有参考入口。两边都受影响时拆清通用责任与项目责任，让每项经验只有一个长期真源。
2. **检查上下文治理**：识别提示、文档、`work.md`、任务胶囊、回执或汇报间的重复信息；判断唯一真源是否精炼、当前事实是否清楚；确认导航、命名和入口能让恢复者快速发现有效信息；为确有恢复价值的内容保留最小入口。
3. **检查业务流转**：为 workflow 和项目实际经过的每个动作标出它独立承载的目标结果、风险覆盖、可恢复性或证据价值。价值重叠的动作合并，没有下游消费者的动作退役；重复汇报、状态搬运、代理性产物、重复验证和习惯性等待都用同一标准判断。
4. **回灌因果改进**：候选说明压缩暴露了什么可观察问题、最小改动会怎样减少下次恢复或执行成本、由哪个既有真源负责，以及调整后如何继续守住风险。压缩只是由真实任务复杂度导致且现有治理已经最小充分时，明确 `no-op`，让现有结构继续承担责任。

责任归属、上下文治理和结果承载三项检查都有结论后，本次压缩治理复盘完成。检查发现的问题仍遵循本文件的接受标准和回灌结果门，由既有长期真源承接。

## 按需加深

出现多次失败、明显范围翻转、跨团队影响、高风险遗漏、昂贵验证或相同问题反复发生时，扩大比较范围，寻找机制而非记流水账。必要时让新视角只读取目标、实际结果、关键差异和证据，检查遗漏风险与不必要复杂度。

平台有可靠遥测时，可用实际 `token`、交互、工具等待和执行时间定位成本；没有可靠遥测就标记未知，不用输出字节、墙钟时间或主观感觉伪造数值。

每个可行动优化候选都作为新的目标交给用户确认。确认前完成事实调查、问题诊断和必要的选择证据；确认后再把方案转成实施责任。一次优化实施完成后仍做一次最小识别，只有新证据产生新问题时才形成新的候选。

项目级更新与 workflow 级更新的需求确认互相独立：可以同时回灌、只选其一、分别延后或放弃。AI 受托代选时也只替用户做该候选的“回灌 / 延后 / 放弃”取舍，不能跳过新目标后续的需求确认和方案确认。

## 接受标准

一条已接受经验应同时具备：

- 明确的未来触发场景；
- 会改变的核心判断或动作；
- 支撑它的事实证据，以及仍属推断的部分；
- 唯一长期责任者与从问题找到它的入口；
- 适用边界，避免把一次性条件泛化为永久规则。

暂时答不清这些问题时，将内容保留为一次性事实；条件齐备后再形成已接受经验。经验候选经协调者接受后，才成为后续任务可消费的稳定输入。

## 与交付的并行边界

等待外部交付时，只读分析可并行，用于收集不依赖最终状态的偏差候选；不并行定稿，最终接受必须在交付事实之后。线上表现、发布差异、回滚效果和真实交付成本只能从实际结果学习，不能提前推断。预判不写入长期真源，也不触发外部写入。

## 停止与缺口回流

- 项目级更新与 workflow 级更新都没有稳定复用价值：展示双 `no-op`，不要求用户回复，结束；
- 候选已被接受并明确唯一责任者与消费入口：展示问题诊断、推荐方案与验收，等待用户确认；
- 用户确认回灌：只建立独立新目标，另从需求澄清与方案确认开始推进；
- 缺少结果或交付证据：返回 `prove` 或 `deliver`，不靠回忆补齐；
- 经验暴露原结果仍未完成：返回产生缺口的 `frame`、`plan`、`execute` 或 `recover`；
- 需要用户改变长期取舍或授权：给出推荐与影响，等待决定；
- 只有当前项目有效：留在项目责任者，不泛化到 `workflow`。
