# 经验复盘

## 负责什么

在没有交付目标时，于结果已经验真后；在有交付目标时，于交付状态已经确定后，判断这次有什么值得改变未来决策。结果稳定且存在潜在复用价值，是本文件的触发信号。复盘不是固定长总结，也不要求每个任务都新增文档；没有稳定复用价值时，最优结果就是 `no-op`。

只有已经出现稳定复用价值信号时才进入 `learn`：有真实交付目标时遵循 `prove → deliver → learn`，没有交付目标时在 `prove` 后进入；无信号就直接完成。任何线程发生上下文压缩，都视为稳定复用价值信号并必须进入本门；压缩事件不直接证明治理存在缺陷，完成规定检查后仍可得到 `no-op`。`learn` 不负责发布，也不能修改交付事实。

## 最小入口与最小动作

用一次最小偏差检查回答：原本预计什么、实际发生什么、差异有什么证据、哪个早期信号下次会改变行动。没有明显偏差、风险、返工或可复用收益时，以 `no-op` 结束，默认不持久化这个空结果。发生过上下文压缩时，必须先完成下面的上下文治理与流程奥卡姆检查，不能因结果成功而直接略过。

只基于实际证据提候选，不把模型感想、成功叙事或偶然噪音直接升级为长期规则。

## 默认快路

1. 发生过上下文压缩时，先执行本文件的压缩专项检查；否则找出造成最多返工、等待、`token`/交互浪费或风险暴露的一个事实。没有可行动发现就 `no-op`。
2. 把它写成经验候选：未来什么场景触发、会改变哪个决定或动作、证据是什么、应由哪个唯一真源承接。
3. 检查现有代码、测试、配置、`README`、项目规则或技能是否已经表达；找到唯一责任者和入口，不为经验另建竞争真源。
4. 等交付事实确定后再接受涉及交付的经验。协调者确认消费价值、证据和责任者后，才将候选变为已接受经验。接受候选不等于完成回灌，也不能直接修改长期真源。
5. 实际回灌是一项新的状态变更：在现有授权和范围内可直接成为下一就绪责任，不重复询问，但仍走最小 `plan → execute → prove`；需要外部写入时再走 `deliver`。超出授权时只形成后续提案。
6. 清理只用于本次判断的临时材料；需要审计、回滚或恢复的证据进入已有证据系统，不另建档案流程。

## 上下文压缩触发的专项检查

上下文压缩是审计触发器，不是缺陷结论。基于压缩前后可见事实、恢复时重新查找或重建的内容、重复加载与交接痕迹进行判断；平台没有可靠遥测时不虚构 `token` 数、压缩损失或成本。

1. **先找唯一责任者**：只在当前项目成立的问题回到项目级 `harness`、项目规则或代码入口；跨项目反复成立的问题回到 workflow `harness` 或本技能现有参考入口。两边都受影响时拆清通用责任与项目责任，不创建第三份竞争真源。
2. **审计上下文治理**：检查是否在提示、文档、`work.md`、任务胶囊、回执或汇报间重复同一信息；唯一真源是否混入流水、过期事实或非承重细节而不够精炼；导航、命名和入口是否让恢复者难以发现当前真源；是否因缺少最小恢复入口而被迫重新加载大段背景。
3. **审计业务流转**：逐个检查 workflow 实际经过的动作与项目级 `harness` 动作。若删除或合并某动作后，目标结果、风险覆盖、可恢复性和证据强度都不下降，就删除或合并；重点质疑与目标关联弱的重复汇报、状态搬运、代理性产物、重复验证和习惯性等待。
4. **只回灌因果改进**：候选必须说明压缩暴露了什么可观察问题、最小改动会怎样减少下次恢复或执行成本、由哪个既有真源负责，以及删除动作为何不会显著扩大风险。压缩只是由真实任务复杂度导致且现有治理已经最小充分时，明确 `no-op`，不为了证明复盘发生过而新增文档、摘要或检查器。

只有完成责任归属、上下文治理和流程奥卡姆三项检查后，压缩触发的复盘才可停止。专项检查发现的问题仍遵循本文件的接受标准和回灌结果门，不在复盘中直接改写长期真源。

## 按需加深

出现多次失败、明显范围翻转、跨团队影响、高风险遗漏、昂贵验证或相同问题反复发生时，扩大比较范围，寻找机制而非记流水账。必要时让新视角只读取目标、实际结果、关键差异和证据，检查遗漏风险与不必要复杂度。

平台有可靠遥测时，可用实际 `token`、交互、工具等待和执行时间定位成本；没有可靠遥测就标记未知，不用输出字节、墙钟时间或主观感觉伪造数值。

候选若会改变当前用户目标、长期偏好、权限边界或责任者，必须交给用户决定；只是契约内安全、可逆且已有责任者的小改进，可作为后续计划候选，不在复盘中悄悄实施。

## 接受标准

一条已接受经验应同时具备：

- 明确的未来触发场景；
- 会改变的核心判断或动作；
- 支撑它的事实证据，以及仍属推断的部分；
- 唯一长期责任者与从问题找到它的入口；
- 适用边界，避免把一次性条件泛化为永久规则。

答不清这些问题就保留为一次性事实或删除。经验候选不能冒充已接受经验；未经接受也不能成为下个任务的强制前置。

## 与交付的并行边界

等待外部交付时，只读分析可并行，用于收集不依赖最终状态的偏差候选；不并行定稿，最终接受必须在交付事实之后。线上表现、发布差异、回滚效果和真实交付成本只能从实际结果学习，不能提前推断。预判不写入长期真源，也不触发外部写入。

## 停止与缺口回流

- 没有稳定复用价值：`no-op`，结束；
- 候选已被接受并明确唯一责任者与消费入口：经验判断完成；实际回灌另按最小结果门推进，或在未授权时形成后续提案；
- 缺少结果或交付证据：返回 `prove` 或 `deliver`，不靠回忆补齐；
- 经验暴露原结果仍未完成：返回产生缺口的 `frame`、`plan`、`execute` 或 `recover`；
- 需要用户改变长期取舍或授权：给出推荐与影响，等待决定；
- 只有当前项目有效：留在项目责任者，不泛化到 `workflow`。
