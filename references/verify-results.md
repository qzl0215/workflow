# 验收结果

## 何时进入

实现产物已形成，准备声明 Task、Plan 或整体业务结果完成时进入。它是所有任务必经的证据 owner，只回答“结果是否真的做成”；commit、push、merge、deploy、公开发布和其他外部写入由条件交付 harness 负责，不能用授权或发布状态替代验收。

## 已知输入

- 已确认范围、Task/Plan/业务验收、非范围和风险；
- 实际 diff、产物、source fingerprint、运行环境与影响面；
- 执行现场、Task 绑定、目标基线、freshness 来源、可写性与脏改动归属；
- 定向、相邻、集成、clean-room 或真实使用验证路径；
- Bug 诊断若涉及共享机制或不变量，已有根因闭环、同源影响集、审计边界和停止依据；
- 已有 RC 证据回执、失败、未覆盖项和最易过期事实。

## 深度判断

按影响面选择 Quick、Standard 或 Full：局部可逆任务做定向检查；跨模块或用户路径增加相邻回归和构建；安全、迁移、高风险、多环境或生产形态敏感任务需要完整门。验证矩阵来自实际变更和业务验收，不照抄历史命令。

默认用户不审代码：用户确认业务结果和风险，AI 负责 diff 自审、范围核对、fresh 验证和机器可读门禁；项目确有独立 reviewer 时可增加正交复核，但仍不把代码判断转嫁给非技术用户。

## 核心动作

1. 从当前验收和实际 diff 建清单；适用时核对红→绿→整理证据。
2. 在声明前 fresh 运行或复用身份完全相同的有效 RC 回执，检查 exit code、关键输出、产物 freshness、覆盖范围和环境。
3. 依次通过 Task → Plan → 整体业务；历史绿灯、实现者自报、部分日志和“应该通过”不是证据。
4. AI 总协调者完成 diff 自审并确认关键路径已有有效回执；真实独立 reviewer 只有能增加正交证据时才复核，任一失败都回到执行任务、根因回路或上游缺口。
5. 记录未覆盖项和残余风险；不能用低层单测替代真实业务验收。
6. 当改动改变客户端消费的响应身份、排序、归属或过滤语义，且客户端存在跨刷新持久缓存时，把缓存契约纳入验收：证明版本化、失效或兼容迁移有效，并覆盖带旧缓存的升级路径或等价自动化；只测空缓存不算完成。无持久缓存不增加此门。

### 根因闭环证据门

局部单点错误只需证明局部原因、原始失败转绿并完成相称验证，不强制生成三层大型报告。诊断结果已确认是共享机制级修复或系统不变量问题时，验收必须读取而不重新决定修复范围，并同时具备：

1. **症状证据**：原始失败用例由红转绿，用户观察到的错误不能按原路径复现。
2. **机制证据**：已证实根因能够解释原始现象，被破坏的不变量已在正确公共边界恢复，实际 diff 不是只在末端绕过症状。
3. **影响面证据**：共享消费者已完成有边界检查，纳入范围的同源问题已处理，相邻回归和上层验收通过，未覆盖项与残余风险透明，并有证据支持当前停止依据。

共享机制级修复若只证明原始页面恢复，验收门不通过，返回根因回路补机制证据和影响面证据；单一低层测试不能替代整体结果。

### RC 证据回执与复用

1. Task 阶段运行定向证据；Plan 汇合只补未覆盖的相邻或集成证据；完整门留给已经收敛、干净且可交付的唯一 RC。
2. 可复用证据生成 **RC 证据回执**，稳定键为 `command-scoped source tree/hash + verification command + environment class`。源码身份是该命令可能读取的规范内容树：干净 Git 内容使用相关 tree，归档、安装包或 dirty 输入使用规范文件清单 hash；路径和 commit 元数据不进入身份。命令身份包含实际命令及会改变语义的 runner/验证器版本；环境类别包含会影响结果的 OS、runtime、依赖和运行形态。
3. 同一输入不得重复运行同一检查；dirty 现场、失败结果、缺字段回执和无法证明环境同一性的结果只能诊断，不能复用为 RC 绿灯。
4. `impact set` 只记录命令相关范围和局部失效依据，不绑定目录。command-scoped 内容、相关依赖、命令语义或环境类别不变时，commit、merge、复制目录和相同制品不得使回执失效；变化时只使受影响证据失效。无关提交和文档变化不得机械作废业务 full，跨真实环境边界与发布后入口 smoke 永远 fresh。
5. 高风险或生产形态敏感 Task 在完整门前完成**生产形态预检**，按风险验证 `cold / warm`、真实规模与历史形态、超时取消与资源峰值、`payload / 缓存 / 序列化`；不适用项写原因，不建设无 owner 的 benchmark 仪式。

### 六问流程奥卡姆门

完成前只问：专家会诊是否改变推荐；subagent 是否产生正并行收益；方法包是否解决真实瓶颈；新增文档是否改善决策或恢复；本次验证是否产生新证据；状态更新是否改变决策或恢复能力。答案为否的未执行步骤直接删除，已发生的重复成本只记一条改进事实。轻/标准任务把回执写在最终回复，复杂项目可在现有 `progress.md` 写一行；不创建独立报告。

### 浏览器驱动故障与产品证据分流

1. 同一可见操作连续尝试两种可见控制方式仍失败，或连接器诊断累计达到 90 秒时，停止在验收主链继续调驱动；记录**驱动故障**，并与**产品验收**分开。
2. 若验收目标不是点击动作本身，改用直达 URL、ready 信号、可见业务内容、网络状态和已有回归契约组合 fresh 证据；只报告实际覆盖的产品结果。
3. 若验收目标就是交互本身且替代证据不能证明，明确未覆盖并返回 Task 或 blocker；连接器失败不得写成产品通过，也不得靠无限重试制造完成感。

## 写入真源

复杂项目把命令、exit code、scoped source hash、impact set、环境类别、RC 回执、未覆盖项和残余风险写入 `progress.md`；标准任务只有持久恢复真源时写最小回执，否则留在最终回复。证据门通过后更新唯一状态；需要外部交付时只传已验证 RC、授权和目标，不复制验证流水。

## 停止 / 通过

证据覆盖所有纳入范围且 fresh 通过，实际结果可报告为“本地已验证”。没有交付请求时必须经过**收尾复盘门**，不得直接完成；存在已授权外部交付时先进入条件交付 harness，由其在真实交付结束后经过同一门。验收通过不自动证明已经提交、合并、部署或线上生效。

## 失败回路 / 能力缺口

测试或真实使用失败返回执行任务或根因回路；验收本身错误返回上游动作。无浏览器、运行环境或独立 reviewer 时使用实际可得证据并声明未覆盖项，不伪造通过；关键用户结果无法证明时保持 blocker。
