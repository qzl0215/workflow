# 编排协作

宿主允许委派，且独立任务、独立证据或复核能缩短工作或降低风险时使用。是否协作和并行度由实际收益决定；工具不可用时单体完成，验收不降级。

给执行者足够的目标、必要输入、可写范围、完成条件和依赖。稳定背景给入口，关键的一次性约束直接说明。上下文包与返回结果默认内联；跨会话恢复才保存文件。

## 串并行编排

方案确认后，有 3 块以上可独立验收的工作时使用，做法取自 pua 的 p9。本机装有 `p9` 时调用它并按它的协议执行，包括旁白和给子代理的 PUA 行为注入；没装就按下面做，关键节点用一行旁白标明，如 `[P9-分配]`、`[P9-验收]`。少于 3 块就自己直接做。

1. 先查现状再拆，不凭记忆拆。画出依赖：互不依赖的并行，在同一条消息里一起派出；有依赖的等前置验收通过再派；共享资源串行。一批超过 5 个就分批。
2. 每个任务写清六件事：为什么做、交付物及各自的验收、只改哪些文件、资源边界、完成的定义（哪些命令通过）、不要做什么。执行者读完不需要再问文件在哪。“先定测试”定下的接缝和第一条失败测试写进交付物。
3. 文件域不交叉；并行改代码用独立工作树。
4. 编排者不替执行者写代码，只定义、分配、验收。执行者说完成时自己跑完成定义里的命令，看到输出才算。
5. 没通过就判断原因：任务没写清就补全重发，粒度太大就拆小，能力不够就换执行者或升模型。返工多先查任务写得清不清。
6. 全部通过后验证整体结果，直到方案写明的交付范围完成。

## 写入与状态

写入必须有明确所有权、可检测冲突和恢复方式。可以使用独立工作树、互不冲突的文件范围，或返回补丁后统一应用；选择宿主真正支持的机制。共享 Git 索引、生成目录、端口、数据库和部署目标等无法安全并行的资源串行处理。不要在没有协调机制时并发修改同一文件。

每任务当前状态只有一个写者；已明确转交状态维护的专属执行者直接写原任务，协调者平时读取，其他参与者返回实际产物、证据、失败与未覆盖项。写权交接须确认旧写者停止且无未决请求，新写者读回后接手；线程终态不自动转移写权。主责任者核对范围、证据适用性和集成结果，不能只采用执行者的完成自述。

任务或输入可能在异步执行期间变化时，绑定任务版本或输入身份。`work_context.py` 可从旧版或当前 `work.md` 提取任务并计算摘要；它的 `dispatchable` 仅表示状态可派发，不验证真实授权，哈希也不证明内容正确。普通任务不要求这些字段。

出现冲突或过期结果时只重做受影响范围；高风险判断需要独立复核时从实际产物与要求开始，不继承实现者结论。所有任务结束后验证整体结果；没有净收益的协作及时收敛。
