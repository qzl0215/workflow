# 大事开工前

走大事流程或用户要求质询时使用。大事指新功能、改版、上生产、难回退或方向不清的任务；用户随时可以说直接做，定时和无人值守任务算已确认。多花的时间和用量都放在这里，开工后要快。

| 步骤 | 做什么 | 过关条件 |
|---|---|---|
| 1 澄清需求 | 查现状 → 按三问写出“我的理解” → 只问推不出的 | 新问题不再改变目标 |
| 2 需求契约 | 让用户确认做的是正确的事 | 用户确认 |
| 3 方案选项 | 让用户确认用正确的方式做 | 用户选定 |
| 4 开干 | 收成执行简报，见 [执行](plan.md) | 做到方案写明的范围 |

前一步没过关不做后一步。

## 1 澄清需求

本机装有 `grilling` 时调用它，代码需求加 `domain-modeling`；两种做法都先做完下面两件事。

### 查现状

- 先读用户级和项目级记忆里已记的背景和偏好；记过的不再问。
- 代码任务先对齐远端最新：取远端，查本地落后多少，落后就同步再读。现场有未提交改动或同步会冲突时不强行合并，对照远端最新版本读，并说明看的是哪个版本。
- 事实自己查，不问用户；范围大就交给子代理，用最快的模型、低推理强度，只带回结论和位置。

### 写出“我的理解”

按根入口“先理解需求”的三问推测，写成“我的理解”，放在提问和契约的最前面。

- 每一问写出依据：原话、记忆或查到的事实；没有依据的标明是推测。
- 用户确认或纠正后，把会反复用到的背景和偏好按 [项目记忆](learn.md) 记下。

### 带着前提提问

- 把要定的事按依赖排好，分轮问：每轮问完现在能答的全部问题并编号，依赖本轮答案的留到下一轮。
- 每个问题附推荐和理由，让用户回“是”就等于接受。
- 挑战方案，包括自己的推荐：它靠哪个假设成立，什么观察能推翻它，有没有更简单或可回退的做法。
- 代码需求：用户的词和项目词表或代码行为对不上时当场指出，定下叫法；用边界场景逼出概念之间的界线。
- 新问题不再改变目标就停。用户要求质询时，提问就是本轮交付，不替用户回答后直接出方案。

## 2 需求契约

| 契约项 | 写什么 |
|---|---|
| 我的理解 | 用户是谁、痛点是什么、真正需求是什么；已确认和推测分开标 |
| 需求 | 按真正需求，这次要做成什么 |
| 事实 | 查到并用上的关键事实 |
| 现状和目标 | 现在怎样，想深之后要变成怎样 |
| 验收 | 可失败：看到什么算成，看到什么算没成 |

按段落写估计超过约 400 字时，现状和目标不写成段落，做成一份可视化对照，其余几项各留几行：

- 左现状、右目标，同一维度同一行；只列有变化的维度，变化处标出。
- 流程、结构或界面有变化的，配一张前后示意图，只画变的部分；全新的东西只画目标。
- 用词专业、质朴、简短：写事实和数字，不用形容词和口号。
- 宿主能渲染就出成图或页面，不能就用对照表加文字示意。顺序：我的理解，需求和事实，对照，验收。

## 3 方案选项

给 2–3 个真互斥的方案，推荐在前；只有一种可行做法就说明原因，不凑数。

| 每个方案写 | 内容 |
|---|---|
| 变化 | 做完和现在比变了什么，收益和要背的代价 |
| 风险 | 最可能让它失败的假设 |
| 验收 | 怎么验收。代码任务写在哪几个公开接口上测、第一条会失败的测试是什么；预期值来自需求或算好的样例，不用被测代码重算 |
| 交付到哪一步 | 默认做到发布上线并在真实入口验过，用户选定即授权到这一步，合并或发布前不再问一次；只有难回退或影响超出方案写明的才另停 |

| 需求类型 | 额外附上 |
|---|---|
| 新算法、新口径、数据规则这类探索型需求 | 3–5 个真实样例的判定结果 |
| 差异在视觉或交互上、文字讲不清 | 页面或样例，装有 `page-craft` 时用它；改现有页面在真实源码上做，不另搭模拟页 |
| 其余 | 短表 |

演示只证明方向可供判断，不是成品验收。

契约和方案都用短句、业务语言、图表优先，只留影响决定的信息。做成页面时版式取自 [页面版式库](../templates/pages.html)，取法见 [汇报](report.md) 的“呈现”。工时按 AI 实际执行时长估。

## 4 开干

用户选定后连续做到方案写明的范围，不逐步请示；结果与预期出入较大或出现没想到的风险才打断，并给推荐。
