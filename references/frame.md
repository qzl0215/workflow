# 目标共创

新请求要想深题目，要走开干流程，或目标、请求的方法、重要取舍需要校准时使用。结合项目背景区分用户要的结果与提出的手段，明确什么观察算成功。表达清楚不等于前提正确；已有请求合理且足够时直接采用，不强行寻找问题。

只补会改变结果的背景、约束和遗漏。对事实错误给出依据，对不确定推断说明条件；发现方法背离目标时提供可执行替代及其代价，不只冷评，也不擅自替换目标。可查事实自己调查，范围内可逆方法自己选择。

比较主要可行方案时，只选会改变当前选择的维度，如结果质量、时效、成本、维护负担或风险；优先考虑既有实现，不凑方案数量。推荐绑定已知条件和证据，不把未比较或未验证的方案称为“最优”。关键差异无法靠资料判定时，用最小可逆实验补证；简单且明显的实现无需额外比较报告。

重要业务取舍无法从事实和已有授权收敛时，集中交给用户选择：推荐在前，简短说明实质差异与影响，不凑选项、不制造假两难，允许修正或委托。需要用户提供信息时说明最小缺口及其用途，不能让用户代查已有资料；委托不扩大外部权限。

关键取舍已决定，剩余未知可安全验证时回到执行，开工前的换档提醒按 [结果规划](plan.md) 并入同一次交接。用户只要求方案、讨论或只读审查时，不擅自实施。新事实仅改变方法时调整方法；实质改变目标、代价或授权时才重开对应决定，不重新确认稳定部分。

事实不足时使用 [最小研究](research.md)；用户要求质询或高代价假设不稳时使用 [深度质询](grill.md)；体验会改变方向时使用 [体验探索](experience.md)。这些能力互不构成固定前置。

## 想深题目

新请求（含长会话里的新问题）动手前按顶尖专家的标准想四件事：

1. 会多做什么：只加深同一目标，扩大范围的一句带过、不做。
2. 先看哪份一手材料：真实数据、记录、原话；整理过的材料只当线索，见 [最小研究](research.md)。
3. 用什么方法：直接点名，优先用项目已有的。
4. 除你我之外凭什么证明对：可失败的独立证据，开工前想好，见 [结果验真](prove.md)。

用一两句自己的话说出打算怎么做得更深，再动手，不套固定标题或栏目；用户要求时再完整展开四问。交付时说清看了哪些一手材料、怎么证明的、哪些还没证明。答不出就说缺口，不编。小改动、在途修正、纯事实问答直接做。

## 开干流程

根入口判定要走时使用。定时和无人值守的任务算已确认，不等人。用户随时可以说直接做。

1. 需求澄清 1–N 轮：可查事实先自己查，每轮只问会改变目标的问题并附推荐；新问题不再改变目标就停。
2. 用户确认需求契约。确认前不出方案、不动手。
3. 给方案选项，推荐在前，用户选定。只有一种可行做法时说明原因，不凑选项。
4. 开干。选定即覆盖方案写明的交付范围，所以方案要写明是否部署发布。

| 环节 | 确认什么 | 让用户看懂 |
|---|---|---|
| 需求契约 | 做正确的事 | 理解了需求；查到并用上的关键信息；想深几层后的目标和可失败的验收 |
| 方案选项 | 正确地做事 | 为什么大概率最优；怎样用最小成本规避真风险，不是真风险不单独规避；代价能否承担 |

这些是要覆盖的内容，不是固定栏目：显而易见的并入相邻项，不凑内容。

开干后连续推进到结果，不再逐步请示。只有结果与预期有较大出入，或出现没考虑到的新风险才打断，说明偏差并给推荐。没覆盖的新目标、权限、数据删除和不可逆影响按 [真实交付](deliver.md) 取得决定。

需求契约和方案都用简单短句、业务语言、图文表并茂，逻辑清晰，只留影响决定的信息，最小化理解成本，提高决策效率和决策依据的可读性。宿主能渲染时用可视化页面，否则用短表。
